= Logging
:idprefix:
:idseparator: -
:docinfo: shared

{project-name-full} uses the https://www.slf4j.org/[SLF4J] logging facade for logging, with the broker assembly providing https://logging.apache.org/log4j/2.x/manual/[Log4J 2] as the logging implementation.
Logging is configured by a properties file in the broker instance `etc` directory.
Which file is used depends on how the broker is invoked.
The `run` command uses `log4j2.properties`.
By default it logs to both the console and a file.
Every other CLI command uses `log4j2-utility.properties`.
By default that logs only errors to the console, alongside the usual command output.

There are a handful of general loggers available:

|===
| Logger | Description

| rootLogger
| Logs any calls not handled by the specific loggers

| org.apache.activemq.artemis.core.server
| Logs the core server

| org.apache.activemq.artemis.utils
| Logs utility calls

| org.apache.activemq.artemis.journal
| Logs Journal calls

| org.apache.activemq.artemis.jms
| Logs JMS calls

| org.apache.activemq.artemis.integration.bootstrap
| Logs bootstrap calls

| org.apache.activemq.audit.base
| audit log.
Disabled by default

| org.apache.activemq.audit.resource
| resource audit log.
Disabled by default

| org.apache.activemq.audit.message
| message audit log.
Disabled by default
|===

== Log Codes

Log entries written at `INFO` level and above carry a special code.
This code is always the first thing in the message and is separated from the text by a colon:

----
2026-02-19 09:53:23,462 INFO  [org.apache.activemq.artemis.core.server] AMQ221043: Protocol module found: [artemis-server]. Adding protocol support for: CORE
----

A code is the `AMQ` prefix followed by a number, here `AMQ221043`.

The code is a contract.
The text of a message may be reworded, corrected, or given more detail in a later release, but its code will not change.
That makes the code, rather than the wording, the thing to match on.
Monitoring and log analysis tools can key off a code without having to care how the message happens to be phrased, and administrators get a stable handle on the individual entries they want to treat specially.

To suppress a particular code in your logging configuration see <<suppressing-a-specific-log-code>>.

== Configuring a Specific Level for a Logger

Sometimes it is necessary to get more detailed logs from a particular logger.
For example, when you're trying to troublshoot an issue.
Say you needed to get TRACE logging from the logger `org.foo`.

Then you need to configure the logging level for the `org.foo` logger to `TRACE`, e.g.:

----
logger.my_logger_ref.name=org.foo
logger.my_logger_ref.level=TRACE
----

== Suppressing a Specific Log Code

Levels are often too blunt an instrument for singling out one entry, because a single logger can emit many different codes.
To act on an individual code use an `ArtemisLogCodeFilter`, listing the codes you want to suppress.
Codes are given *without* the `AMQ` prefix, since every log code carries it:

----
appender.log_file.filter.suppressed.type = ArtemisLogCodeFilter
appender.log_file.filter.suppressed.codes = 222061,224000
----

Here `suppressed` is just a name you choose for the filter; any name will do, as long as it is used consistently.

By default a matching entry is discarded and a non-matching entry is left for the rest of the configuration to decide on.
This can be changed with the optional `onMatch` and `onMismatch` attributes, which can be `ACCEPT`, `DENY`, and `NEUTRAL`.

So that a missing entry is never a mystery, the filter reports what it is suppressing.
As soon as the configuration takes effect it logs a single entry naming every code it will discard:

----
AMQ160000: Log entries with the following codes are being suppressed by the logging configuration: 222061, 224000
----

This is logged once.
Nothing is reported when `onMatch` is set to something other than `DENY`, since the filter is then not suppressing anything.

=== Choosing Where to Attach the Filter

A filter attached to an appender, as above, affects only that appender.
This is usually what you want, and it is the cheapest option.
For example, to keep an entry in `artemis.log` while keeping it off the console, attach the filter to the `console` appender only.

A filter can also be attached to an individual logger:

----
logger.artemis_server.filter.suppressed.type = ArtemisLogCodeFilter
logger.artemis_server.filter.suppressed.codes = 222061
----

Finally, a filter declared at the top level of the file applies everywhere:

----
filter.suppressed.type = ArtemisLogCodeFilter
filter.suppressed.codes = 222061
----

[WARNING]
====
Prefer an appender or logger filter over a top-level one.
A top-level filter is evaluated by Log4J 2 *before* the configured level is checked, so it runs even for `DEBUG` and `TRACE` calls on hot code paths which the level would otherwise discard immediately.
Attaching the same filter to each appender instead costs nothing on those paths.
====

=== What the Filter Matches

The filter only recognizes a code where the contract puts it: at the very beginning of the message, before any parameters are substituted into it.

A code which reaches the log some other way is not matched.
In particular, if an entry's text happens to contain a code because an exception message was substituted into it, that code belongs to whatever threw the exception and not to the log entry itself, so suppressing it will not discard that entry.
This is deliberate, and means that suppressing one code can never silently discard an unrelated entry.

=== Why Not RegexFilter?

Log4J 2 ships a general-purpose `RegexFilter` which can be used to achieve the same goal as `ArtemisLogCodeFilter`.
However, there are a few problems with `RegexFilter` which `ArtemisLogCodeFilter` does not have:

* The configuration of `RegexFilter` is not particularly intuitive, even for such a simple use-case.
* It can be triggered by a code that is not the entry's own, such as one from a substituted exception message.
* It is slower than `ArtemisLogCodeFilter`, potentially much slower depending on the configuration.

== Configuration Reload

Log4J2 has its own configuration file reloading mechanism, which is itself configured via the same log4j2.properties configuration file.
To enable reload upon configuration updates, set the `monitorInterval` config property to the interval in seconds that the file should be monitored for updates, e.g.
----
# Monitor config file every 5 seconds for updates
monitorInterval = 5
----

== Logging in a client application

Firstly, if you want to enable logging on the client side you need to include a logging implementation in your application which supports the SLF4J facade.
Taking Log4J2 as an example logging implementation, since it used by the broker, when using Maven your client and logging dependencies might be e.g.:

[,xml,subs="normal"]
----
<dependency>
   <groupId>org.apache.artemis</groupId>
   <artifactId>artemis-jms-client</artifactId>
   <version>{project-version}</version>
</dependency>
<dependency>
   <groupId>org.apache.logging.log4j</groupId>
   <artifactId>log4j-slf4j2-impl</artifactId>
   <version>{log4j-version}</version>
</dependency>
----

The `ArtemisLogCodeFilter` described in <<suppressing-a-specific-log-code>> can be used in a client application too, assuming it's using Log4j2 as the logging implementation.
It ships with the broker, so it is available there automatically, but a client has to add a specific dependency:

[,xml,subs="normal"]
----
<dependency>
   <groupId>org.apache.artemis</groupId>
   <artifactId>artemis-log-code-filter</artifactId>
   <version>{project-version}</version>
</dependency>
----

It is then configured exactly as it is on the broker.

The Log4J2 configuration can then be supplied via file called `log4j2.properties` on the classpath which will then be picked up automatically.

Alternatively, use of a specific configuration file can be configured via system property `log4j2.configurationFile`, e.g.:

----
-Dlog4j2.configurationFile=file:///path/to/custom-log4j2-config.properties
----

The following is an example `log4j2.properties` for a client application, logging at INFO level to the console and a daily rolling file.

----
# Log4J 2 configuration

# Monitor config file every X seconds for updates
monitorInterval = 5

rootLogger.level = INFO
rootLogger.appenderRef.console.ref = console
rootLogger.appenderRef.log_file.ref = log_file

logger.activemq.name=org.apache.activemq
logger.activemq.level=INFO

# Console appender
appender.console.type=Console
appender.console.name=console
appender.console.layout.type=PatternLayout
appender.console.layout.pattern=%d %-5level [%logger] %msg%n

# Log file appender
appender.log_file.type = RollingFile
appender.log_file.name = log_file
appender.log_file.fileName = log/application.log
appender.log_file.filePattern = log/application.log.%d{yyyy-MM-dd}
appender.log_file.layout.type = PatternLayout
appender.log_file.layout.pattern = %d %-5level [%logger] %msg%n
appender.log_file.policies.type = Policies
appender.log_file.policies.cron.type = CronTriggeringPolicy
appender.log_file.policies.cron.schedule = 0 0 0 * * ?
appender.log_file.policies.cron.evaluateOnStartup = true
----

== Configuring Broker Audit Logging

There are 3 audit loggers that can be enabled separately and audit  different types of broker events, these are:

. *base*: This is a highly verbose logger that will capture most  events that occur on JMX beans.
. *resource*: This logs the creation of, updates to, and deletion of resources such as addresses and queues as well as authentication.
The main purpose of this is to track console activity and access to the broker.
. *message*: This logs the production and consumption of messages.

[NOTE]
====


All extra logging will negatively impact performance.
Whether or not the performance impact is "too much" will depend on your use-case.
====

These three audit loggers are disabled by default in the broker `log4j2.properties` configuration file:

----
...
# Audit loggers: to enable change levels from OFF to INFO
logger.audit_base.name = org.apache.activemq.audit.base
logger.audit_base.level = OFF
logger.audit_base.appenderRef.audit_log_file.ref = audit_log_file
logger.audit_base.additivity = false

logger.audit_resource.name = org.apache.activemq.audit.resource
logger.audit_resource.level = OFF
logger.audit_resource.appenderRef.audit_log_file.ref = audit_log_file
logger.audit_resource.additivity = false

logger.audit_message.name = org.apache.activemq.audit.message
logger.audit_message.level = OFF
logger.audit_message.appenderRef.audit_log_file.ref = audit_log_file
logger.audit_message.additivity = false
...
----

To _enable_ the audit log change the level to `INFO`, like this:

----
logger.audit_base.level = INFO
...
logger.audit_resource.level = INFO
...
logger.audit_message.level = INFO
----

The 3 audit loggers can be disable/enabled separately.

Once enabled, all audit records are written into a separate log file (by default `audit.log`).
